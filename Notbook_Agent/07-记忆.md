# 一、记忆

记忆系统是 AI 智能体的核心能力之一。它使智能体能够：

- **记住历史对话**：在多轮对话中保持上下文连贯
- **学习用户偏好**：跨会话积累用户信息
- **积累知识经验**：从交互中提取并持久化关键事实

LangChain 1.0 将记忆系统分为两大类：

| 记忆类型     | 生命周期     | 存储方式                       | 典型场景               |
| ------------ | ------------ | ------------------------------ | ---------------------- |
| **短期记忆** | 单次会话     | Checkpointer                   | 多轮对话上下文保持     |
| **长期记忆** | 跨会话持久化 | redis ，关系数据库，向量数据库 | 用户偏好、关键事实存储 |

```
智能体记忆系统

┌─────────────────────┬───────────────────┐
│    短期记忆          │     长期记忆        │
│  (会话内上下文)       │   (跨会话持久化)    │
│                     │                     │
│  ┌───────────────┐ │  ┌───────────────────┐ │
│  │  Checkpointer │ │  │ redis				   │ │
│  └───────────────┘ │  └───────────────────┘ │
│                     │                     │
│  开发：InMemorySaver │  开发：redis         │
│  生产：PostgresSaver │  生产：redis         │
└─────────────────────┴───────────────────┘
```

# 二、短期记忆

短期记忆就像人的"工作记忆"——在当前对话过程中记住之前说过的话，一旦对话结束或清除，记忆就会丢失。

不能跨对话框交流

## （一）核心机制：`Checkpointer`

短期记忆通过 **`Checkpointer`**（检查点保存器）实现。它会在每轮对话结束后保存完整的对话状态（包括消息历史、工具调用记录等），下一轮对话开始时自动加载。

**关键参数：`thread_id`** —— 区分不同对话线程的标识。相同 `thread_id` 的对话共享同一段记忆，不同 `thread_id` 的对话互相独立。

## （二）开发环境方案（内存）：`InMemorySaver`

`InMemorySaver` 将对话状态保存在内存中，适合开发和测试

### 3. 流程

- **智能体（Agent）**：像是一个“金鱼记忆”的办事员。它本身记不住任何东西，每处理一件事，都必须依赖外部提供的历史记录。
- **内存记忆检查点（InMemorySaver）**：相当于一个“临时档案柜”。它负责在程序运行期间，安全地保管所有的对话记录。
- **会话标识（thread_id）**：相当于档案袋上的“专属标签”。它确保了不同用户或不同对话之间的记忆是完全隔离的。

**1. 记忆的存储（写档案）**
当你向智能体发起第一次提问时，智能体处理问题并生成回答。随后，LangGraph 框架会在后台自动将“你的提问”和“智能体的回答”打包成一个完整的包裹。框架会读取你配置中的 `thread_id`，给这个包裹贴上对应的标签，并将其存入 `InMemorySaver` 这个档案柜中，若此次为第一次对话，则存入前该档案柜为空。

**2. 记忆的获取（查档案）**
当你基于同一个 `thread_id` 发起第二次提问时，框架会拿着这个标签去档案柜里精准找到之前的包裹，把里面的历史记录取出来。接着，框架会将“旧的历史记录”与“你的新问题”合并成一整叠纸，一起交给智能体。智能体看到了完整的上下文，就能给出连贯的回答。

**3. 记忆的更新（覆盖旧档）**
智能体针对新问题生成回答后，框架会把“旧历史 + 新问题 + 新回答”重新打包，再次贴上原来的 `thread_id` 标签，放回档案柜中。也就是说，柜子里永远保存着当前会话**最新、最完整**的那一份对话记录。

- **会话隔离**：如果你传入了一个新的 `thread_id`，框架就会去打开一个全新的空抽屉，智能体自然会“失忆”。只有保持 `thread_id` 一致，才能实现多轮对话。
- **生命周期限制**：`InMemorySaver` 本质上是一个 Python 字典，数据仅存在于程序运行时的内存中。一旦程序终止或重启，所有的对话历史都会瞬间丢失。
- **生产环境建议**：`InMemorySaver` 仅适合本地开发和快速调试。如果要推向生产环境，必须将其替换为 `PostgresSaver` 或 `SqliteSaver` 等持久化存储方案，以确保数据的可靠性和服务的连续性。

## （三）生产环境方案（数据库）：`PostgresSaver`

### 1. `PostgresSaver`

在生产环境中，推荐使用 PostgreSQL 数据库作为检查点存储，确保记忆不会因服务重启而丢失

安装依赖：

```
pip install langgraph-checkpoint-postgres -i https://mirrors.aliyun.com/pypi/simple/
```

**PostgresSaver 会自动在数据库中创建 4 张以 `checkpoint` 开头的表：**

- **`checkpoints`** -- 存档目录
    - 这是最核心的表，用于存储每一次对话轮次（或称“超步”）的完整状态快照。
    - 它记录了当前对话的 `thread_id`、状态版本号、以及指向实际状态数据的指针。
    - 你可以把它理解为游戏存档的“目录”或“索引”，它告诉你“在哪个时间点，存了哪一份存档”。

- **`checkpoint_blobs`** -- 存档内容
    - 用于存储实际的、序列化后的状态数据（即“存档内容”）。
    - `checkpoints` 表中的指针会指向这里。
    - 由于对话历史、工具调用结果等数据可能非常大，LangGraph 将其压缩并存储为二进制大对象（BLOB），以节省空间和提高读写效率。
    - 这个表就是你的智能体真正“记住”的内容。

- **`checkpoint_writes`** -- 临时草稿
    - 记录在当前状态快照之后、但尚未被正式合并到主状态中的“待处理写入”。
    - 当一个节点执行完毕但整个流程还未完成时，它的输出会先写到这里。
    - 这确保了即使程序在执行中途崩溃，重启后也能从断点处恢复，继续处理这些未完成的写入，避免数据丢失或重复执行。

- **`checkpoint_migrations`** -- 版本记录
    - 这是一个元数据表，用于跟踪数据库结构的版本和迁移历史。
    - 当 LangGraph 库升级并修改了上述三个表的结构时，它会通过这个表来确保你的数据库 schema 与代码版本保持同步，防止因结构不匹配导致的错误。

### 3. 检查点（Checkpoint）存储机制

**核心现象**

在 LangGraph 中，数据库记录的检查点（Checkpoint）数量通常远大于实际对话轮数。例如，3轮对话往往会产生 9 条记录（在postgres的4个表中能看到）

**产生原因**

LangGraph 的状态持久化是**按执行步骤（Super-step）**而非按对话轮次记录的。一次完整的“提问-回答”交互，底层通常包含 3 个关键节点流转：

- **Agent 节点**：模型思考并决定下一步动作。
- **Tool 节点**：执行工具调用并返回结果。
- **结束/输出节点**：模型生成最终回复。

因此，每一轮对话都会产生 3 个独立的检查点快照（3轮 × 3步 = 9条记录）。

**记录结构**

这些记录通过 `checkpoint_id` 和 `parent_checkpoint_id` 形成一条严格的链式时间线，精准保存了每个微小步骤的完整状态。

**核心优势**

- **时间旅行（Time Travel）**：支持回滚到任意中间状态（如工具刚执行完时），修改数据后重新执行后续步骤。
- **断点续跑**：程序崩溃时，可从最近保存的中间检查点无缝恢复，无需从头重跑。
- **全链路追踪**：为复杂 Agent 提供极高精度的执行轨迹，便于调试与复盘。

# 三、长期记忆（没写代码）

在真实的 AI 产品中，用户希望 AI 能够记住自己的信息

这种**跨会话、跨时间**保存的信息，就称为**长期记忆（Long-Term Memory）**

**长期记忆示意图**：

```
           用户输入
               │
               ▼
       LLM 提取长期信息
               │
               ▼
        Redis 持久化存储
               │
               ▼
        下次聊天读取记忆
               │
               ▼
       Prompt 注入长期记忆
               │
               ▼
            LLM 回答
```

长期记忆最大的特点：即使程序关闭，重新启动以后，用户的信息仍然存在

# 四、摘要记忆中间件

`SummarizationMiddleware` 是 LangChain 提供的一个中间件组件，用于在 Agent 对话中自动管理上下文窗口。当对话历史积累到一定程度时，它会自动将较早的消息压缩为摘要，从而在有限的上下文窗口中保留最重要的信息，防止因 token 超限导致的对话中断或上下文丢失

**核心价值**：

- 让 Agent 能够处理持续数小时甚至数天的长对话
- 避免因超出 LLM 上下文窗口限制而丢失关键上下文
- 控制 token 消耗，降低 API 调用成本

**流程**：

- 当用户向 Agent 提出问题时，Agent 首先会检查当前累积消息的 Token 数量是否达到了预设的阈值：

    - **若未达到阈值**：说明上下文长度在安全范围内，Agent 将正常处理当前消息并继续对话。

    - **若达到或超过阈值**：为了防止超出大模型的上下文窗口限制，Agent 会触发记忆压缩机制。
        - 首先，系统会对较早的历史消息生成一段精简的摘要；
        - 其次，系统会丢弃（或截断）那些被压缩过的旧消息；
        - 最后，系统只保留最近的消息和刚刚生成的摘要。
        - 经过这一轮上下文“瘦身”后，Agent 再基于精简后的信息进行思考，并最终向用户返回结果。

**API**：

```
#摘要记忆中间件
SummarizationMiddleware( 
    model=model,
    trigger=("tokens", 10),  # 超过10个token就触发摘要（降低阈值）
    keep=("messages", 1)	# 摘要完成以后，保留最近的 1 条消息
)
```

from tool.SendEmailTool import send_email_tool

    2. 任务：
        - 请根据下面提供的历史对话生成摘要

        - 只提取用户的姓名

    model=model,

    ],  # 当token达到10个触发摘要，生成环境建议3000

    config = {"configurable": {"thread_id": thread_id}}
    state = agent.get_state(config)
    messages = state.values.get("messages", [])

    print("消息数量：", len(messages))
    for i, message in enumerate(messages):

        print("类型：", type(message).__name__)
        # 只打印前500个字符，避免输出太长

        print("内容：")
        print(content[:500])
    print("==============================================\n")
