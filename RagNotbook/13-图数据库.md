# 一、图数据库

图数据库（Graph Database）是一类专门用来存储、查询和管理**图结构数据**的数据库系统。它基于数学中的“图论”（Graph Theory），将数据建模为**节点（Node/Vertex）**、**边（Edge/Relationship）\**和\**属性（Property）**，而不是传统关系型数据库中的表和行。

## （一）核心概念

**节点（Node）**：代表实体，如人、公司、地点、文章等。

**边（Edge）**：代表节点之间的关系，如“认识”、“购买”、“位于”等。边是有方向的，也可以带有属性。

**属性（Property）**：节点和边上都可以附带键值对形式的属性，用于描述具体特征。

## （二）为什么需要图数据库？

在关系型数据库中，表达复杂关系需要大量的 `JOIN` 操作，随着关系层级加深，查询性能会急剧下降。而图数据库将**关系作为一等公民**直接存储，遍历关系的时间复杂度接近 O(1)，因此在处理高度关联的数据时具有显著优势。

## （三）典型应用场景

**社交网络**：好友推荐、影响力分析、社区发现

**知识图谱**：语义搜索、智能问答、推理引擎

**风控与反欺诈**：识别团伙作案、资金链路追踪、异常交易检测

**推荐系统**：基于用户行为图的个性化推荐

**供应链/IT基础设施管理**：依赖关系分析、故障根因定位

## （四）主流图数据库产品

**Neo4j**：最流行的原生图数据库，使用 Cypher 查询语言

**Amazon Neptune**：AWS 托管图数据库，支持 Gremlin 和 SPARQL

**JanusGraph**：开源分布式图数据库，底层可对接 Cassandra/HBase

**TigerGraph**：专注于大规模图分析，支持深度链接遍历

**NebulaGraph / HugeGraph**：国内开源图数据库，在中文社区活跃度高

## （五）与关系型数据库的关键区别

| 维度         | 关系型数据库         | 图数据库           |
| ------------ | -------------------- | ------------------ |
| 数据模型     | 表、行、列           | 节点、边、属性     |
| 关系表达     | 外键 + JOIN          | 显式边，直接存储   |
| 多跳查询     | 性能随跳数指数下降   | 性能稳定，近线性   |
| Schema灵活性 | 严格预定义           | 灵活，可动态扩展   |
| 适用场景     | 事务处理、结构化报表 | 关联分析、路径探索 |

简而言之，如果业务核心在于 **“事物之间的关系”** 而非事物本身，图数据库通常是比关系型数据库更合适的选择。

# 二、Neo4j

## （一）介绍

Neo4j 是目前全球**最流行、使用最广泛的原生图数据库**，由瑞典 Neo4j, Inc. 公司开发。它于 2007 年发布首个版本，是图数据库领域的标杆产品，几乎所有图数据库的教程和对比都会以它为参照。

### 1. 核心特点

1. **原生图存储引擎**
    Neo4j 从底层就是为图数据设计的（Native Graph Storage），而非在关系型数据库上套一层图的抽象。节点和边在磁盘上通过指针直接相连，遍历时只需"跳转"到相邻记录，无需索引查找或 JOIN，因此多跳查询性能极高且可预测。

2. **Cypher 查询语言**
    Neo4j 创造了 **Cypher**——一种声明式、ASCII-art 风格的图查询语言，语法直观易读：

    ```cypher
    // 查找 Alice 的朋友的朋友，并返回共同好友数量
    MATCH (a:Person {name:'Alice'})-[:FRIEND]->(f)-[:FRIEND]->(fof)
    WHERE fof <> a
    RETURN fof.name, COUNT(f) AS mutualFriends
    ORDER BY mutualFriends DESC
    ```

    Cypher 现已成为图查询语言的事实标准，并被开放为 openCypher 规范，被 Amazon Neptune、Memgraph 等多种图数据库兼容。

3. **属性图模型（Property Graph）**

    - 节点可以有多个标签（Label）和任意键值对属性
    - 边有类型（Type）、方向和属性
    - Schema 可选：既支持严格约束（Constraint/Index），也允许动态扩展

4. **ACID 事务保证**
    与许多 NoSQL 图数据库不同，Neo4j 完整支持 ACID 事务，适合对数据一致性要求高的生产环境。

5. **丰富的生态工具链**

    - **Neo4j Browser / Bloom**：可视化探索界面
    - **Neo4j Desktop**：本地开发管理工具
    - **GDS（Graph Data Science）**：内置 60+ 图算法（PageRank、社区发现、节点嵌入等）
    - **APOC**：400+ 实用过程/函数库
    - **驱动**：官方提供 Java、Python、Go、JavaScript、.NET 等语言驱动
    - **ETL 工具**：支持从 CSV、JSON、RDBMS、Kafka 等导入数据

### 2. 版本与部署

| 版本               | 说明                                                         |
| ------------------ | ------------------------------------------------------------ |
| Community Edition  | 开源免费（GPLv3），单机部署，适合学习和中小项目              |
| Enterprise Edition | 商业授权，支持集群（Fabric/Causal Clustering）、RBAC、监控、热备份等企业级特性 |
| Neo4j Aura         | 全托管云服务，按需弹性扩缩容                                 |

### 3. 典型应用场景

- **知识图谱**：企业知识库、语义搜索、智能客服
- **实时推荐**：电商"买了又买"、内容平台相似推荐
- **金融风控**：关联交易识别、洗钱路径追踪、担保圈分析
- **IT 运维**：CMDB 依赖拓扑、故障影响面分析
- **生命科学**：蛋白质相互作用网络、药物靶点发现
- **社交网络**：好友推荐、影响力传播模拟

### 4. 局限性

- **单机扩展瓶颈**：Community 版不支持水平扩展；Enterprise 的 Fabric 虽可分片，但跨分区查询仍有开销
- **超大规模写入**：相比专为批量写入优化的分布式图数据库（如 JanusGraph + Cassandra），Neo4j 在十亿级边以上的写入吞吐可能受限
- **学习成本**：虽然 Cypher 比 SQL 更适合图，但从关系型思维转换仍需适应期
- **商业版价格较高**：企业级功能需付费授权

> Neo4j 是图数据库的"MySQL"——生态最成熟、文档最完善、社区最活跃，是学习和落地图技术的首选起点；当数据规模或并发超出其能力边界时，再考虑分布式替代方案。

## （二）数据模型

Neo4j 采用的是**属性图模型（Property Graph Model）**，这是目前图数据库领域最主流、最实用的数据建模方式。它比纯数学图论更贴近真实业务，核心由三个基本元素构成：**节点（Node）**、**关系（Relationship）** 和**属性（Property）**。

### 1. 三大核心元素

#### 节点（Node）

- 代表一个**实体**，如一个人、一家公司、一篇文章、一个城市等。
- 可以有零个或多个**标签（Label）**，用于分类和索引。例如一个节点可以同时拥有 `:Person` 和 `:Employee` 两个标签。
- 可以包含任意数量的**键值对属性**。
- 在 Cypher 中用圆括号表示：`(n:Person {name: "Alice", age: 30})`

#### 关系（Relationship）

- 代表两个节点之间的**有向连接**，如 `KNOWS`、`WORKS_AT`、`PURCHASED`。
- **必须有且仅有一个类型（Type）**，且方向明确（从起点指向终点）。虽然查询时可以忽略方向遍历，但存储时方向是固定的。
- 同样可以携带**属性**，例如 `[:PURCHASED {date: "2024-01-15", amount: 99.9}]`。
- 在 Cypher 中用方括号和箭头表示：`-[r:PURCHASED {amount:99.9}]->`

#### 属性（Property）

- 节点和关系上都可以附加的**键值对**。
- 支持的类型包括：字符串、整数、浮点数、布尔值、日期时间、数组（同类型）、点坐标（Point）等。
- **不支持嵌套对象或异构数组**（如需复杂结构，通常拆分为子节点或使用 JSON 字符串）。

### 2. 关键设计原则

| 原则                     | 说明                                                         |
| ------------------------ | ------------------------------------------------------------ |
| **关系是一等公民**       | 关系不是通过外键隐式关联，而是作为独立实体显式存储，可带属性、可被查询、可建索引 |
| **标签用于分类而非继承** | 标签是轻量级的分组标记，支持多标签，但不构成类层次结构（无继承语义） |
| **Schema 可选但推荐**    | Neo4j 不强制预定义 Schema，但生产环境强烈建议创建约束（Constraint）和索引（Index）以保证数据质量和查询性能 |
| **避免超级节点**         | 单个节点连接数百万条边会导致遍历性能骤降，应通过中间节点拆分或重新建模规避 |
| **关系方向应有业务含义** | 即使逻辑上是双向的（如"朋友"），也需选定一个方向存储；必要时可存两条反向边 |

### 3. 与关系型模型的对比

| 维度       | 关系型数据库       | Neo4j 属性图               |
| ---------- | ------------------ | -------------------------- |
| 实体表示   | 表中的一行         | 节点                       |
| 关系表示   | 外键 + JOIN        | 显式边（一等公民）         |
| 多对多关系 | 中间关联表         | 直接边（可带属性）         |
| 分类机制   | 表名 / type字段    | 多标签（Label）            |
| 灵活性     | 修改Schema成本高   | 动态加标签/属性，无需ALTER |
| 遍历效率   | 随JOIN层数指数下降 | 指针直连，O(1)跳转         |

### 4. 建模示例：电商场景

```cypher
// 用户下单购买商品
(:User {id:1, name:"Alice"}) 
  -[:PLACED {orderId:"ORD-2024-001", time:datetime()}]-> 
    (:Order {status:"shipped"})
      -[:CONTAINS {quantity:2, unitPrice:49.9}]-> 
        (:Product {sku:"SKU-A100", name:"无线鼠标"})

// 商品属于多个类目
(:Product {sku:"SKU-A100"}) -[:BELONGS_TO]-> (:Category {name:"电子产品"})
(:Product {sku:"SKU-A100"}) -[:BELONGS_TO]-> (:Category {name:"办公外设"})
```

在这个模型中：

- `Order` 作为独立节点而非用户表的字段，因为订单本身有状态、时间等丰富属性；
- `CONTAINS` 关系携带了数量和单价，避免了额外的订单明细表；
- 商品通过多条 `BELONGS_TO` 边自然表达多类目归属，无需关联表。

### 5. 常见建模陷阱与建议

- ❌ **把关系当节点用**：除非关系本身需要被其他关系引用（即"关系的元关系"），否则不要将普通关系提升为节点。
- ❌ **过度使用属性存储列表**：如将好友ID存为数组属性，会丧失图遍历能力。应拆为独立边。
- ✅ **利用关系属性替代中间节点**：如果关联表只有少量描述字段，直接用关系属性即可。
- ✅ **为高频查询路径建立复合索引**：如 `CREATE INDEX FOR (p:Product) ON (p.category, p.price)`。
- ✅ **定期分析图模式**：使用 `CALL apoc.meta.graph()` 可视化实际数据结构，及时发现超级节点或异常模式。

> **总结**：Neo4j 的属性图模型以"节点-关系-属性"三元组为基础，通过将关系显式化、可属性化，实现了对现实世界关联结构的自然映射。掌握其建模精髓的关键在于：**让关系承载业务语义，而非仅仅作为连接手段**。

## （四）Cypher

### 1. 创建 -- CREATE

`CREATE` 命令用于在 Neo4j 中创建节点和关系。通过它，可以定义节点的属性、标签以及节点之间的关系。以下为常见的几种用法：

**创建数据库：**

```
CREATE DATABASE 数据库名;
```

**创建无属性节点：**

```
CREATE (变量名:节点标签)
```

**创建带属性节点：**

```
CREATE (变量名:节点标签 { 属性名:属性值, 属性名：属性值, ..., 属性名:属性值})
```

**创建关系 - 无属性节点之间：**

```
CREATE (变量名:节点标签)-[:关系类型（两节点之间的关系）]->(变量名:节点标签)
```

**创建关系 - 有属性节点之间：**

```
CREATE 
	(变量名:节点标签 {属性集合（多个键值对）})
	-[:关系类型（两节点之间的关系）]
	->(变量名:节点标签 {属性集合（多个键值对）})
```

**创建多个标签（节点）：**

```
CREATE (变量名:节点标签1:节点标签2 { 属性名:属性值, 属性名：属性值, ..., 属性名:属性值})
```

### 2. 匹配/创建 -- MERGE

`MERGE` 是 Cypher 中最强大也最需要谨慎使用的子句之一。它实现了"存在即匹配，不存在则创建"的原子操作

**创建/匹配单个节点：**

```
MERGE (变量名:节点标签 {属性名:"匹配的属性值"})  RETURN 返回匹配到/创建的节点
```

**创建/匹配多个节点：**

```
UNWIND ['属性值1', '属性值2', '属性值3'] AS 别名
MERGE (变量名:节点标签 {属性名:"别名"})  RETURN 返回匹配到/创建的节点.属性名
```

**创建初始化属性：**

```
MERGE (变量名:节点标签 {属性名: '属性值'})
ON CREATE SET 
  变量名.属性名 = '属性值',
  变量名.属性名 = '属性值'
RETURN 变量名
```

**匹配更新属性：**

```
MERGE (变量名:节点标签 {属性名: '属性值'})
ON MATCH SET 
  变量名.属性名 = '属性值',
  变量名.属性名 = '属性值'
RETURN 变量名
```

**创建/匹配整个路径：**

```
MERGE (变量名1:节点标签1 {属性名1:"属性值1",属性名2:"属性值2"}) 
    - [变量名:关系类型 {属性名3:"属性值3"}] 
    -> (变量名2:节点标签2 {属性名4:"属性值4"}) 
    RETURN 变量名1,变量名,变量名2
```

**匹配节点后再创建关系（推荐）：**

```
-- 先匹配两个已存在的节点
MATCH (变量名1:节点标签1 {属性名1:"属性值1",属性名2:"属性值2"}),
	(变量名2:节点标签2 {属性名4:"属性值4"}) 
    
-- 然后创建或匹配他们之间的关系
MERGE (变量名1) -[变量名:关系类型] ->(变量名2) 
on CREATE set 
	变量名.属性名 ="属性值" 
RETURN 变量名1,变量名,变量名2
```

**批量更新多个节点的属性：**

```
UNWIND [
  {name: '马云', company: '阿里巴巴'},
  {name: '马化腾', company: '腾讯'},
  {name: '任正非', company: '华为'}
] AS person_data
MERGE (p:Person {name: person_data.name})
ON MATCH SET 
	p.company = person_data.company
RETURN p
```

**批量创建多个节点：**

```
UNWIND ['蔡崇信', '张勇', '彭蕾'] AS name
MERGE (p:Person {name: name}) RETURN p.name
```

**批量创建关系：**

```
MATCH (company:Company {name: '阿里巴巴'})
UNWIND ['蔡崇信', '彭蕾', '张勇'] AS cofounder_name
MERGE (person:Person {name: cofounder_name})
MERGE (person)-[r:WORKS_AT]->(company)
RETURN person,r
```

### 3. CREATE vs MERGE

| 特性 / 命令  | CREATE                                    | MERGE                                                        |
| ------------ | ----------------------------------------- | ------------------------------------------------------------ |
| **作用**     | 永远创建一个新的节点或关系                | 如果不存在就创建，存在就匹配（类似 “查找或创建”）            |
| **重复数据** | 每次执行都会新增节点或关系，不检查重复    | 避免重复，先 MATCH 查找，找不到再 CREATE                     |
| **使用场景** | 确定要新增数据，允许重复                  | 希望保证节点或关系唯一，避免重复                             |
| **属性设置** | 可以直接用 `SET` 设置属性                 | 可以用 `ON CREATE SET`（仅在创建时设置）和 `ON MATCH SET`（匹配时更新） |
| **效率**     | 快，直接创建                              | 先匹配再创建，略慢一些                                       |
| **例子**     | `cypher CREATE (p:Person {name:'Alice'})` | `cypher MERGE (p:Person {name:'Alice'})`                     |

### 4. 查找 -- MATCH

`MATCH` 命令用于在 Neo4j 中查找节点、关系和路径。它相当于 SQL 里的 `SELECT`，是最常用的查询语句

**查找某标签的所有节点：**

```
MATCH (变量名:节点标签) RETURN 变量名
```

**查找节点并按属性筛选：**

```
MATCH (变量名:节点标签 {属性名: '属性值'}) RETURN 变量名
```

**查找存在某关系的节点：**

```
MATCH (变量名1:节点标签1)-[:关系类型]->(变量名2:节点标签2) RETURN 变量名1, 变量名2
```

**查找节点之间存在的关系的属性：**

```
MATCH (变量名1:节点标签1)-[变量名:关系类型]->(变量名2:节点标签2) RETURN 变量名1, r, 变量名2
```

**查找任意长度的路径：**

在图数据库里，一条 **路径** 是由 **节点 (nodes)** 和 **关系 (relationships)** 组成的，**每经过一条关系，就算一次 hop（跳）**，**hops 数 = 路径上关系的数量**

- 匹配 **1 hop**：查找和 Alice 直接相连的朋友
- 匹配 **2 hops**：查找 Alice 的“朋友的朋友”
- 匹配 **1 到 3 hops**：查找 Alice 在 1~3 跳以内能到达的朋友

```
MATCH path（路径变量名） = 
(变量名1:节点标签1)
-[*min..max]（可变长度关系模式，匹配指定长度范围内的路径，min为最小跳数，max为最大跳数）
->(变量名2:节点标签2)
RETURN path
```

### 5. CREATE 和 MATCH

创建两节点之间的关系，从**创建节点 → 建立关系 → 查询结果**完整步骤

- 创建节点

```
CREATE (p:Person {name: "马云", birthYear: 1964}) RETURN p;
CREATE (c:Company {name: "阿里巴巴", foundedYear: 1999}) RETURN c;
```

- 建立关系

```
MATCH (p:Person {name: "马云"}), (c:Company {name: "阿里巴巴"})
CREATE (p)-[r:FOUNDED {role: "创始人", startYear: 1999}]->(c)
RETURN p, r, c;
```

- 查询验证

```
MATCH (p:Person {name: "马云"})-[r:FOUNDED]->(c:Company)
RETURN p.name, r.role, r.startYear, c.name, c.foundedYear;
```

### 6. 条件 -- WHERE

`MATCH` 用于查找图中的节点和关系，`WHERE` 用于对匹配到的结果增加过滤条件

**语法格式：**

```
MATCH (<node-variable>:<Label>)
WHERE <条件表达式>
RETURN <返回的字段或表达式>
```

### 7. 修改 -- SET

`SET` 用于修改节点或关系的属性，也可以用来为节点或关系添加标签

**设置或更新节点属性：**

```
MATCH (<node-variable>:<Label> { <条件> })
SET <node-variable>.<Property-name> = <Property-value>
RETURN <node-variable>
```

**给节点添加标签：**

```
MATCH (<node-variable>:<Label> { <条件> })
SET <node-variable>:<NewLabel>
RETURN <node-variable>
```

**更新关系属性：**

```
MATCH (<node1>:<Label1>)-[r:<RELATION_TYPE>]->(<node2>:<Label2>)
SET r.<Property-name> = <Property-value>
RETURN r
```

**同时设置多个属性：**

```
MATCH (<node-variable>:<Label> { <条件> })
SET <node-variable> += { <Property1>: <Value1>, <Property2>: <Value2>, ... }
RETURN <node-variable>
```

### 8. 排序 -- ORDER BY

`ORDER BY` 用于对 MATCH 或 RETURN 查询的结果进行排序，可以按节点或关系的属性升序或降序排列

`ORDER BY` 必须放在 **RETURN** 或 **WITH** 之后

```
MATCH (<node-variable>:<Label>)
RETURN <返回的字段或表达式>
ORDER BY <字段或表达式> [ASC|DESC]
```

### 9. 限制 -- LIMIT

`LIMIT` 用于限制查询结果的数量，常用于分页或者只取前几条数据

`LIMIT` 必须放在 **RETURN** 或 **WITH** 后面

```
MATCH (<node-variable>:<Label>)
RETURN <返回的字段或表达式>
LIMIT <数量>
```

### 10. 跳过 -- SKIP

`SKIP` 用于跳过查询结果的前几条记录，常与 `LIMIT` 搭配实现分页查询

`SKIP` 必须放在 **RETURN** 或 **WITH** 后面，并且一般与 `ORDER BY` 搭配使用，否则分页结果不稳定

```
MATCH (<node-variable>:<Label>)
RETURN <返回的字段或表达式>
ORDER BY <字段或表达式>
SKIP <数量>
LIMIT <数量>
```

### 11. 空 -- NULL

`NULL` 表示 **节点或关系属性不存在或未定义**，类似 SQL 中的空值

在 Cypher 查询中，如果引用不存在的属性，返回结果就是 `NULL`

设置默认值避免 NULL，使用`coalesce(a, b)`函数，返回第一个非 NULL 的值

**特性：**

| 特性         | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| **默认值**   | 节点或关系没有某个属性时，查询该属性返回 `NULL`              |
| **逻辑判断** | `NULL` 在布尔表达式中不会被当作 `TRUE` 或 `FALSE`，需要用 `IS NULL` 或 `IS NOT NULL` 判断 |
| **计算参与** | `NULL` 参与运算结果仍为 `NULL`（例如 `5 + NULL = NULL`）     |
| **排序**     | 排序时，`NULL` 默认排在最后（ASC）或最前（DESC）             |

### 12. 判断 -- IN

`IN` 用于判断某个值是否包含在指定的列表（数组）中，常用于条件筛选

```
MATCH (<node-variable>:<Label>)
WHERE <值> IN <列表>
RETURN <返回字段>
```

### 13. UNION 和 UNION ALL

`UNION` 和 `UNION ALL` 用于 **合并两条或多条查询语句的结果**

它将两组结果中的公共行组合并返回到一组结果中。 它不从两个节点返回重复的行

UNION ALL 和 UNION 使用方式基本相同，只是返回的结果不会过滤掉重复行

结果列类型和来自两组结果的名称必须匹配，这意味着列名称应该相同，列的数据类型应该相同，如果这两个查询不返回相同的列名和数据类型，那么它抛出一个错误

查询结果的列的前缀不同也会报错，所以需要用 AS 关键字给查询的列取别名

```
<查询语句1>
UNION [ALL]
<查询语句2>
```

| 特性         | UNION               | UNION ALL                      |
| ------------ | ------------------- | ------------------------------ |
| **是否去重** | 是，自动去重重复行  | 否，保留所有重复行             |
| **使用场景** | 不希望结果重复时    | 希望保留所有原始结果，包括重复 |
| **效率**     | 较低，需要去重      | 较高，不去重                   |
| **语法**     | `查询1 UNION 查询2` | `查询1 UNION ALL 查询2`        |

### 14. 删除 -- REMOVE

`REMOVE` 用于 **删除节点或关系的属性**，或 **删除节点的标签**

`REMOVE` **不会删除节点或关系本身**，只删除属性或标签

```
MATCH (<node-variable>:<Label> { <条件> })
REMOVE <node-variable>.<Property-name>
RETURN <node-variable>
```

**删除节点标签：**

```
MATCH (<node-variable>:<Label> { <条件> })
REMOVE <node-variable>:<Label-to-Remove>
RETURN <node-variable>
```

**删除关系属性：**

```
MATCH (<node1>:<Label1>)-[r:<RELATION_TYPE>]->(<node2>:<Label2>)
REMOVE r.<Property-name>
RETURN r;
```

### 15. 删除 -- DELETE

`DELETE` 用于 **删除节点或关系本身**

注意：如果节点有关系，必须先删除关系或使用 `DETACH DELETE`

**DELETE 只删除节点或关系本身，不删除属性**（使用 `REMOVE` 删除属性）

**删除无关系节点：**

```
MATCH (<node-variable>:<Label> { <条件> })
DELETE <node-variable>
```

**删除某节点及其所有关系：**

```
MATCH (<node-variable>:<Label> { <条件> })
DETACH DELETE <node-variable>
```

**删除关系：**

```
MATCH (<node1>:<Label1>)-[r:<RELATION_TYPE>]->(<node2>:<Label2>)
DELETE r;
```

**清空：**

```
MATCH (n) DETACH DELETE n;
```

### 16. REMOVE vs DELETE

| 操作            | 会删除内容                        | 是否保留属性/元数据                    |
| --------------- | --------------------------------- | -------------------------------------- |
| `DETACH DELETE` | 节点 + 关系 + 节点属性 + 关系属性 | 不保留节点/关系数据，索引/约束仍在     |
| `REMOVE`        | 删除单个属性或标签                | 只删除指定属性/标签，节点/关系本身保留 |

### 17. 约束

约束用于保证数据的唯一性和完整性，Neo4j 会自动维护约束相关的索引

**节点属性唯一性约束：**确保某个标签的节点的某个属性值是唯一的

- 批量添加id属性

```
UNWIND ['蔡崇信', '张勇', '彭蕾'] AS name
MERGE (p:Person {name: name})
SET p.id = randomUUID()
```

- 创建唯一性约束，如果不存在

```
CREATE CONSTRAINT unique_person_id IF NOT EXISTS
FOR (p:Person)
REQUIRE p.id IS UNIQUE
```

- 验证约束，尝试插入重复ID会报错

```
CREATE (:Person {id: 'eac4831e-60ab-4ace-9463-4ee500bcf926', name: 'clover')}
```

**节点属性存在性约束：**确保某个标签的所有节点都拥有某个属性

- 创建存在性约束

```
CREATE CONSTRAINT person_name_exists IF NOT EXISTS
FOR (p:Person)
REQUIRE p.name IS NOT NULL
```

- 验证约束

```
CREATE (:Person {age: 55}) -- 这会失败
CREATE (:Person {name: '马云', age: 55}) -- 这会成功
```

**查看和删除约束：**

```
SHOW CONSTRAINTS

DROP CONSTRAINT unique_person_id IF EXISTS
```

### 18. 索引

索引用于加速查询性能，特别是基于属性的查找

**单属性索引：**加速基于单个属性的查询

- 创建单属性索引

```
CREATE INDEX person_name_index IF NOT EXISTS
FOR (p:Person)
ON (p.name)
```

- 使用

```
MATCH (p:Person {name: '马云'}) RETURN p
MATCH (p:Person) WHERE p.name = '马云' RETURN p
```

**复合索引：**加速基于多个属性组合的查询

- 创建复合索引

```
CREATE INDEX person_name_age_index IF NOT EXISTS
FOR (p:Person)
ON (p.name, p.age)
```

- 使用

```
MATCH (p:Person) WHERE p.name = '马云' AND p.age = 55 RETURN p
MATCH (p:Person) WHERE p.name = '马云' RETURN p -- 也会使用索引
```

**全文索引：**全文搜索引擎会为每个匹配的结果计算一个**相关性分数（Score）**，可以根据这个分数对结果进行排序，让最相关的结果排在最前面。

- 定义

```
CREATE FULLTEXT INDEX personFulltextIndex 
FOR (n:Person|Company) 
ON EACH [n.name, n.age, n.id]
```

- 查询

```
CALL db.index.fulltext.queryNodes("personFulltextIndex", "阿里巴巴") 
YIELD node, score
RETURN node.name, node.description, score
ORDER BY score DESC
```

**查看和删除索引：**

```
--查看索引
SHOW INDEXES

-- 删除索引
DROP INDEX person_name_index IF EXISTS

-- 删除全文索引
CALL db.index.fulltext.drop("personFulltextIndex")
```

import Neo4jUtil
